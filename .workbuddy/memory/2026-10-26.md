## 0.5.3 服务器实测暴露的三个问题 → 0.5.4

用户 `npm i -g forgex-agent@0.5.3` 后在 Ubuntu 上跑 `forgex`，反馈：启动报
`Encountered two children with the same key, \`4\``，以及"这个不能填 key 嘛"。定位到三处：

1. **React key 重复（真 bug）**：`ui/App.tsx` 的 `push()` 把 `id: counter.current` 写在
   `setLines` 的更新函数**内部**，而更新函数在渲染阶段才执行，同一 tick 的多次 push
   （banner/notice/模型切换两条）会读到同一个 counter 值 → 重复 key。
   修法：调用时先 `const id = counter.current` 再进更新函数。
   验证手法：假 TTY（自造 `Writable` stdout + `Readable` stdin，`isTTY=true`、`setRawMode`）
   直接 `render(App)`；旧写法复现 1 条警告、新写法 0 条。临时脚本用完即删，未入库。
2. **`/models` 不落盘**：`writeModelSelection()` 遇到 `path` 不存在直接返回 false，
   于是没跑过 `/connect` 的用户每次切模型都提示"未找到配置文件"。
   改为 `path ?? defaultConfigPath()` + `readExistingConfig` 兜底创建；
   `apiKeyEnv` 按 baseUrl 反查 `PROVIDERS` 预设（DeepSeek → DEEPSEEK_API_KEY）。
3. **Linux 上 Key 无处可存**：`persistApiKey()` 非 win32 只返回一句 export 提示。
   新增 `~/.forgex/credentials.json`（`{keys:{ENV:KEY}}`，强制 0600，坏 JSON 直接覆盖）；
   `loadConfig` 新增 `credentialsPath` / `skipCredentials`，在环境变量缺失时兜底注入
   （优先级低于真实 env）。Windows 仍写用户环境变量，PowerShell 失败时回落凭据文件。

配套：新增 `runtime/api-key.ts`（`apiKeyEnvFor` / `currentApiKeyEnv` / `applyApiKey`），
TUI 与纯文本模式都加了 `/key [<API Key>]`（直接填 Key，不重选 provider），
启动时若无 Key 主动提示 `/connect` 或 `/key`；`ModelConfig` 增加可选 `apiKeyEnv`。
`switchModel` 跨提供方切换时不再沿用旧 Key（改从目标环境变量取，取不到就清空并提示 `/key`），
返回值增加 `savedPath` / `apiKeyEnv` / `keyReady`。

测试：`pnpm test` 852 全绿（新增凭据文件、写配置创建、跨提供方 Key 三类用例）。
版本升到 **0.5.4**，`dist-npm` 已重建（118.5kB / 4 files），发布仍需用户带 2FA 执行。
注意：tsup 产物把中文转成 `\uXXXX` 转义，`grep 中文` 会 0 命中，别据此误判"没打进包"。


## Key "一次性"问题：重开会话丢失 → 三处修复（0.5.4 续改）

用户反馈 `/key` 填的 sk 重开会话就没了。定位到三个叠加原因：

1. **Windows 写用户环境变量只对新终端生效**：同一个窗口里重开 forgex 继承的是旧 env，
   读不到刚写的变量 → 表现为"填一次就没了"。改为**三平台统一写 `~/.forgex/credentials.json`**
   （0600），不再写注册表（少一份明文拷贝，行为也一致）。`persistApiKey(name, value, {path})`
   现在只做文件写入，`execFileSync` / `escapeSingleQuote` 已删除。
2. **`/key` 不写配置**：只存 credential 时，没有配置文件的机器下次启动仍退回
   `127.0.0.1:8000` + `local-model`，Key 读到了却发往错端点，用户照样觉得"没记住"。
   `applyApiKey` 现在同时 `writeModelSelection(...)`，返回值增加 `configSaved` / `configPath`。
3. **`apiKeyEnv` 名字错位**：`writeModelSelection` 按 baseUrl 反查预设，可能把
   「存到 FORGEX_API_KEY」改成「配置指向 DEEPSEEK_API_KEY」，重启后取不到。
   新增 `patch.apiKeyEnv` 显式优先级（`/key` 传入实际存储名）。
   另外 `loadConfig` 的 Key 解析改为 `env[apiKeyEnv] ?? model.apiKey`，避免声明变量缺失时
   把已经从 FORGEX_API_KEY / 凭据文件拿到的 Key 丢掉。

配套：`/connect` 的 `next` 补 `apiKeyEnv: envName`，避免本次会话再 `/key` 按旧名落盘；
TUI 与纯文本 `/key` 输出拆成两行（已更新 / 已保存到哪 / 配置写失败告警）；
`commands/connect.ts` 提示改为回显凭据文件路径；README、docs/SECURITY.md 同步措辞。

验证：temp HOME 会话1 `/models deepseek-v4-pro` + `/key` → 会话2（换目录、无 FORGEX_* env）
显示 `模型: deepseek-v4-pro` + `API Key 状态：已配置`，且无"未检测到 API Key"提示；
注册表未被写入（已清理前几轮测试残留的 FORGEX_API_KEY / DEEPSEEK_API_KEY）。
CLI 测试 78 全绿；`dist-npm` 重建为 0.5.4（119.1kB）。

**遗留（非本次改动）**：工作区里有未提交的 core WIP（step-executor / task-planner /
task-verifier / tool-dispatcher / sub-agent 等），`packages/core/test/step-executor.test.ts`
有 3 个用例失败：新加的 `if (!result.success && result.retryable !== true) break;`

## 收尾：core 重试用例对齐 + Key 可观测性（同日第二轮）

**1. 修掉 3 个失败的 step-executor 用例**（失败源于未提交的 core WIP：新增
`if (!result.success && result.retryable !== true) break;`）。
不改业务语义，改用例——`throw`/未注入 agent 都属于不可重试路径：
- 「首次失败第二次成功」改为返回 `reason:'error' + error.retryable:true + 无 toolResults`
  （这才是允许重放的形态），仍覆盖 failed → ready → running 合法转移；
- 「重试预算耗尽」同法，断言 attemptsUsed=2、step.attempts=2；
- 「未注入 agent」断言改为 1 次（重试也没有执行者）；
- 新增「不可重试失败（鉴权错误）只试一次」「已产生工具调用的失败即使 retryable 也不重放」
  「AgentLoop 抛异常只试一次」三个用例锁住新策略。
`step-executor.ts` 补注释说明重试策略，`runAttempt` 的 catch / 未注入分支显式 `retryable:false`。
结果：`packages/core/test/step-executor.test.ts` 10 个用例全绿，全仓 **860 全绿**。

**2. Key 可观测性**
- `LoadedConfig` 新增 `apiKeySource: 'env' | 'credentials' | 'file' | null` 与 `credentialsPath`；
  `loadConfig` 内部记录「哪些变量是从凭据文件注入的」，据此判定来源（不能只看有没有值）。
- `forgex doctor` 新增独立「API Key」检查项：`sk-****abc（凭据文件 …）` / `（环境变量）` /
  `（配置文件明文）`（后者标 WARN，提示改用 /key）；未配置时回显 `/key` 与 export 用法。
- `forgex config` 输出 `apiKeySource` / `credentialsPath`，脱敏逻辑不变。

**3. `/key` 不带参数 → 隐藏输入**
TUI 新增 `keyEntry` 状态：`/key` 进入掩码输入（复用 `renderInput(..., mask)`），Enter 提交、
Esc 取消、命令面板在该状态下禁用；`applyKey()` 抽成回调，`/key sk-xxx` 与隐藏输入共用同一条
落盘+连通性校验路径。HELP / 命令面板 / README 同步。
验证手法：假 TTY 直接渲染真实 App（自造 Writable/Readable，补 `stdin.ref/unref`，
否则 Ink 5 在 `setRawMode` 时抛 `stdin.ref is not a function`），结果
`{"masked":true,"promptShown":true,"credWritten":true,"envName":"FORGEX_API_KEY","dupKeyWarn":false,"updatedShown":true}`。

**环境坑（重要）**：Bash 工具派生的 shell 会继承父进程环境，用户级环境变量清理后
当前会话里仍然带旧值，测「凭据文件兜底」必须显式 `DEEPSEEK_API_KEY= FORGEX_API_KEY=`
置空，否则会被误判成 `apiKeySource: 'env'`。

`dist-npm` 重建：`forgex-agent@0.5.4`，119.9 kB / 4 files。发布仍需用户带 2FA 手动执行。
